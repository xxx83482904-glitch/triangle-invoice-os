# 通知から返信する

## 普段の使い方

1. Windowsを起動し、正規WeChatで本人がログインします。このアプリも常駐させます。
2. 携帯用HTTPSを開いてアプリの接続キーでログインします。iPhoneはSafariの共有メニューから「ホーム画面に追加」し、追加したアイコンから開きます。
3. アプリの「設定 → 新着通知」で「この端末の通知をオン」を押し、端末の通知許可を本人が選びます。「通知をテスト」で受信を確認します。
4. 「通知音をオン」は、アプリを開いている間の音です。オンにした直後に確認音が鳴ります。
5. 通知を押すと届いた会話を開きます。本文を入力して送信ボタンを押し、宛先と本文を確認して送ります。

チャット一覧と新着順が起動時の標準です。AIの対応候補・優先度順は引き続きメニューから使えます。通知は返信の自動送信をしません。

「送信確認済み」はWindows版WeChatで送信結果を確認した状態です。相手の受信・既読の保証ではありません。「確認不能」では自動再送せず、WeChat側で確認してください。

## PC側の設定

既存の携帯用HTTPS設定を用意し、私有 `.env` の `WECHAT_PUSH_ENABLED=true` で起動します。新しいセットアップでは初期値falseです。初回に `.runtime/webpush-private.pem` を生成し、以降は同じ鍵を使用します。公開鍵だけを認証済み端末へ渡します。秘密鍵・通知先URL・端末の鍵をGitやログに含めないでください。

依存関係は `backend/requirements-lock.txt` に固定しています。`scripts/setup.ps1`、`scripts/start.ps1` の通常手順で起動します。送信は正しいアカウント・独立会話窓・空の入力欄を検証し、本人が指定したテスト送信を確認してから `WECHAT_PLUS_SEND_ENABLED=true` にします。

## 通知するデータと条件

- 登録は接続キーによるログイン後、端末で明示的にオンにした場合だけです。通知先はApple / Google / Mozilla / Microsoftの既知のPushドメインに限定し、HTTPリダイレクトは追いません。
- 外部へは暗号化した汎用の「新着あり」と内部の会話・イベントIDだけを送ります。名前・本文・添付・WeChatアカウントIDは含めません。ロック画面にも本文は出しません。
- 新規受信callbackだけを通知対象にします。履歴の初期読込、添付の保存完了、自分の発言、同一メッセージの再取得では鳴りません。
- 通知イベントと受信本文は同じSQLiteトランザクションで保存します。同じメッセージは1イベント。Push送出の前に処理済みを記録し、不明な結果を再送して何度も鳴らしません。
- 短時間の連続着信は会話ごとにまとめます。読んだメッセージ・2分以上前の通知は送出しません。Pushサービス受付と端末への到達は別の状態です。
- 通知をオフにすると端末登録を削除します。ログアウトでもそのログインに紐づく端末登録を取り消します。閉じている間の汎用通知はアプリのログイン期限と独立しますが、本文の閲覧・返信には有効なログインが必要です。

## 実際の制限

Windowsの電源オフ・スリープ、WeChat未ログイン、未監視の会話では着信を取得できません。UI操作による部分的な監視であり、全友達・全グループの常時同期とは異なります。

iPhoneのバックグラウンド通知はホーム画面アプリと本人の通知許可が必要です。OSの消音・集中モードをアプリから解除しません。音量・通知音・実際の配信は端末側にも依存します。[Apple/WebKitの説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)。

Chromeの自動テストでは、新着から音・会話遷移・Mock返信までと、実Service Workerによる通知API呼出しを確認します。Headless ChromeにはOSの通知表示面がないため、これをiPhoneへの到達・実際の音の確認とは扱いません。携帯では「通知をテスト」を実行し、画面を閉じた状態での到達を別に確認してください。

Web Pushには [pywebpush](https://github.com/web-push-libs/pywebpush) 2.5.0を使用します（MPL-2.0）。提供元の実装を改変せず、暗号化・VAPID署名を利用します。
