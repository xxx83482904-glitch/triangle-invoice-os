# AIを前提にした会話と行動のUI

更新: 2026-11-09。ユーザーの追加要望は、**返信の急ぎ順で会話を並べ、返信案を確認し、次にやることをタスクに入れること**。AIを独立したチャットボット画面に閉じ込めず、普段の会話整理・返信・行動の流れに組み込む。

## 今回実装した操作

- 初期画面は「対応すること」。返信・送信確認の候補、優先件数、未完了タスク数を表示。
- 会話カードに参照メッセージ、優先度、その理由を表示。優先度順／新着順に切り替えられる。
- 優先度は「優先／通常／あとで」、または簡易判定へ戻す操作。手動指定はSQLiteへ保存し、新着が来ても上書きしない。
- 「未読」と「返信候補」は別。開いただけでは返信候補から消えない。保存範囲内で後続の送信確認済みメッセージがあれば候補判定を解除するが、内容に十分回答したかの判定はまだない。
- カードや会話内の返信サポートから、3種類の定型返信案を下書きに入れる。既存下書きは末尾に追加して保持し、4,000文字を超える場合は追加せず案内する。送信ボタンは別操作。
- 「タスク候補を確認」で元の発言、編集可能なタスク名、任意の期限を表示。本人が確定してからSQLiteへ保存する。期限は初期値なし。
- 「タスク」から未完了／完了を切り替え、元のメッセージを直接開ける。別端末の更新は既存WebSocketで反映する。
- チャット一覧にも優先度の並べ替えを追加。モバイルは「対応すること／チャット／タスク／検索／設定」の5つのナビゲーション。

**これはAI接続済み機能ではない。** `LocalRulesProvider` は端末内の簡易ルールで、期限らしい語句・質問・依頼・経過時間を使う。返信案とタスク名は定型文。画面に「AI未接続」と明記し、APIは `ai_connected=false` を返す。ネットワークやモデルを呼ばない。

## 将来のAIで実現する体験

1. **優先順位**: 誰からの何の依頼か、本人宛てか、実際の期限、未回答の論点、相手を待たせている時間を会話から読み取る。新着だけでなく「先に返すべき会話」を説明付きで並べる。
2. **返信案**: 会話の文脈・相手・言語・本人の文体に合う案を出す。「短く／丁寧に／日中翻訳」などを選べる。本人の予定、価格、納期など不明な条件を勝手に承諾しない。
3. **行動への変換**: 「資料を確認」「見積もりを送る」「日程を調整」などのタスク候補を抽出する。期限・担当・内容を本人が編集して確定する。元のメッセージへのリンクを必須にする。
4. **朝や再開時の見渡し**: 急ぎの返信、今日のタスク、相手の返事待ちをまとめる。実装時はデータの最終取得時刻と不足範囲を添える。現時点で返事待ち・日次要約は未実装。

## UIで維持すること

- 優先度の理由と参照メッセージを開ける。判定に自信がない場合やグループの宛先が不明な場合は「要確認」。本人が訂正できる。
- 不足する履歴を推測で埋めず、判定対象範囲と最終分析時刻を表示する。AI停止・失敗時も通常チャットと手動タスクを使えるようにする。
- 返信案を採用しても送信しない。タスク候補を表示しても登録しない。外部カレンダーやタスクサービスへの登録も別の確定操作とする。
- 新着後に古い返信案を表示している場合は更新が必要と知らせる。下書きを自動上書きしない。
- 期限候補には根拠とタイムゾーンを持たせる。相対表現の「明日」はメッセージ日時から解釈し、保存前に確認する。
- 「返信済み」「読んだ」「タスク化した」「タスク完了」は別の状態。タスクを作っただけでは返信済みにしない。

## モジュール境界とAPI

```text
WeChatAdapter → 保存済みメッセージ → AssistantProvider（推論のみ）
                                      ├─ 優先順位と根拠 → 対応すること
                                      ├─ 返信案 → 編集用下書き → 本人が送信 → 既存Send Queue
                                      └─ タスク候補 → 本人が確定 → ローカルtasks
```

現在の境界は `backend/app/assistance.py` の `AssistantProvider` / `LocalRulesProvider`。送信APIやAdapterを呼ぶ権限を持たせていない。UIは `frontend/src/components/attention-center.tsx`、データはマイグレーション `003_assistance_tasks.sql`。

- `GET /api/attention`: 取得済み直近50件／会話を参照した候補と根拠。
- `POST /api/chats/{id}/priority`: 手動優先度、またはautoへ戻す。
- `GET /api/tasks`, `POST /api/tasks`: タスク取得・本人確定後の登録。
- `POST /api/tasks/{id}/state`: 未完了／完了の切り替え。

すべて既存の認証・アクセス制御を通す。タスク登録は受付UUIDによる冪等性を持ち、会話と元メッセージの一致をサーバーで検証する。

本物のAIを追加する際は、外部通信をGETのたびに実行しない。非同期ジョブと結果キャッシュを追加し、参照メッセージID・内容のハッシュ・Providerの版を記録する。新着との競合、タイムアウト、キャンセル、解析失敗、費用上限を扱う。モデルのJSON出力をスキーマ検証し、本文に含まれる指示をツール実行や権限変更に使わない。

## 現在の制限

- 最新50件だけの簡易判定。否定・皮肉・複数の依頼・担当者・古い未回答は正確に理解しない。急ぎではない旨の一部表現は扱うが、期限の意味解析はしない。
- 未確定／失敗した送信が参照範囲にある場合は、送信状態の確認を優先して返信案を停止する。自動再送しない。
- タスクは1つの受信メッセージにつき1件。登録後のタイトル・期限編集、削除、複数タスク抽出、リマインド通知、外部サービス連携は未実装。
- 期限の過去／未来による色分けや通知、返信候補の手動「対応不要」指定、スヌーズ、重要人物設定は未実装。
- 実AIの推論、翻訳、要約、文体学習は未実装。実WeChatの読み取り・送信も引き続き未実装。

## モデル・データの方針

モデルとタスクサービスは未選定。まずアプリ内タスクを利用する。ローカルモデルならWindowsの計算資源を使い、外部APIなら契約・料金・転送先・対象会話・保存方針を本人が確認してから有効にする。APIキーはWindows側だけで扱う。

全会話を外部AIへ自動転送する許可はない。自動整理を追加する場合も、対象チャットと履歴範囲を本人が指定できる設定を先に用意する。画像・音声・ファイルは別の保存・解析モジュールで拡張する。
