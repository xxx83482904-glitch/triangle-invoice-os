## 1. 口座明細の保存

- 日本版の固定バーは「保存…（N件）」1つ。PCでは選択の確認・未確認に戻す操作をバーに残す。スマホでは「選択の操作」メニューに確認・未確認・科目・選択解除をまとめる。
- 状況は「選択 N件／未保存の編集 N件／自動候補 N件」。日本版専用のCSSで44pxの操作領域を1段に配置し、通常60〜61pxのバーを意図する。実測は未実施。
- 保存ボタンから既存BankSavePreviewDialogを開き、先頭の「保存の対象」で切り替える。サーバーから原本の最新値を読み直して既存の競合確認を行い、その変更一覧を確認して保存する。

| 選択肢 | 既存scope | 対象 |
| --- | --- | --- |
| すべての編集（既定） | edited | 表示外を含む全下書き |
| 選択中の明細 | selected | 選択中の下書きと選択中の自動候補 |
| 確認済みにした明細 | reviewed | reviewed=trueの下書き |
| 編集した明細 | edited | 表示外を含む全下書き |

判断:

- 既存editedには確認操作の下書きも含まれる。「すべての編集」と「編集した明細」は同じ集合とし、画面内に説明する。手動編集と確認操作の起源を新しく推定して除外しない。
- 自動候補はselectedだけに含む。読み込みだけでは「すべての編集」が増えない。予測が表示されている行でメモだけ編集しても、保存時には元データへメモの差分だけを適用する。
- 件数0の選択肢はdisabledとし、値を直接渡しても処理しない。編集が0件で選択済みの自動候補だけがある場合は、選択可能なselectedを初期対象にする。全対象が0件なら保存ボタンも無効。
- 選択肢の件数は既存bankSaveIdsによる候補数。読み直した結果、既に保存済みの同一値は既存bankSaveChangesにより除かれ、「変更なし」として表示される。最終保存件数は確認画面の変更一覧の件数。
- 保存対象切替時の失敗は確認画面にも理由を残し、その状態での確定保存を無効にする。下書き・選択は既存の成功応答で確認したIDだけを外す。失敗したバッチ、表示外、対象外の下書きは保持する。既に同じ内容が保存済みと確認できた下書きの整理も既存仕様を維持。
- **未保存のまま別画面へ移動する際の確認**は、従来どおりedited全体のみ。ここでselected等に絞って移動すると残りの編集を失うため、対象セレクトを出さない。
- 口座の保存API・認可・監査・更新日時の競合確認・100件ごとの保存処理は変更していない。

## 2. 分類の根拠と確認状態

表示専用の `bankClassificationPresentation` に対応を集約した。根拠はmutedのバッジ、状態は明確な枠・背景のバッジ。PCでは「根拠 / 状態」列、スマホでは摘要の近くに2つをまとめる。

| 根拠の条件（上が優先） | 表示 |
| --- | --- |
| sourceMissing | 元明細なし |
| TRANSFER / EXCLUDED | 振替 / 対象外 |
| 科目分割 | 科目分割 |
| 科目なし | 候補なし |
| GUESS（旧AI低確度の理由も既存関数で判定） | 推測 |
| HISTORY | 過去実績 |
| RULE | ルール |
| MANUAL | 手動 |
| その他の有効な分類 | 推定 |

- 根拠はreviewedを除いて判定する。確認後に保存元がMANUALになっても、GUESS/HISTORYの確度があれば推測／過去実績を残す。
- 状態は保留を優先し、次にreviewedから確認済み／未確認を出す。保留だからといって元の根拠を推測へ置き換えない。
- 記帳詳細に「分類の根拠と状態」と `classificationReason` の本文を追加。理由がなければ「分類の理由は記録されていません」。スマホ行の既存理由文にも「根拠の理由」を付ける。tooltipだけにはしない。
- 保存された科目・確度・確認状態・理由は変更しない。既存の推測確認ガード（bankClassificationLabel / isGuessClassification）は変更せず、92件を含む既存データの移行・補正はしない。

### 3. 案件の要対応

日本版だけ `projectAttention` の結果を使う。要対応は該当案件数で、複数の理由がある案件も1件。行には理由ごとの書類件数を表示する。

| 条件 | 表示・扱い |
| --- | --- |
| 支払／入金残額があり、期限が基準日より前 | 支払期限超過／入金期限超過 |
| 残額があり、期限が今日〜7日後（両端を含む） | 7日以内の支払い／入金 |
| 発行請求書がDRAFTまたはneedsReview | 書類確認待ち（同じ書類は1件） |
| 受領請求書がOCR_PENDING／REVIEWING／APPROVAL_PENDING | 書類確認待ち |
| PAIDなのに有効な支払記録が不足 | 書類確認待ち。ダッシュボードと同様、期限の督促には重ねない |
| 契約書なし、契約未請求額、WAITING、段階未設定だけ | 要対応に含めない |

- 有効な入出金記録から残額を計算。一部支払は残額があれば対象、全額支払は対象外。削除済み支払記録は使わない。
- 発行側は既存 `isBillableIssuedInvoice`、受領側はP0-5の `receivedPayableSummary` を使う。削除済み、発行の取消、受領のアーカイブ／却下、債務グループの支払対象外を除く。発行のDRAFTは書類確認だけ。
- 期限なし／不正な期限から期限超過を推定しない。上の確認フラグ・状態がある場合は書類確認として表示する。
- 案件がCOMPLETED／ARCHIVEDでも、対象書類に実際の残額・期限があれば追加で抑制しない。削除済み案件は対象外。
- 優先順は期限超過→7日以内→書類確認。最も高い理由で並べ、低い理由が複数ある案件が期限超過を追い越さない。
- 金額表示権限のない利用者には期限の金融情報を送らず、書類確認だけを表示。既存の案件アクセス範囲・権限は維持。
- 「契約書なし」は中立色の「契約書なし（参考）」にする。既存の契約書なしフィルターは残す。
